## 为什么选择 Unagikuma

- **一台机器就够用。** 下载一个文件,运行它,打开浏览器,大约 30 秒监控和告警就能工作。第二台机器或集群是以后按需加的,不是起步的前提。
- **只有一个文件,不用装别的。** 支持 Linux、macOS、Windows 和 FreeBSD。
- **该查的都能查。** 网站、服务器、端口、Ping、DNS、SSL 证书,以及域名到期时间。
- **告警发到你常用的地方。** 邮件、Telegram、Slack、Discord、飞书、钉钉、企业微信、Webhook 等。
- **一个问题,不会告警刷屏。** 如果是你自己的网络断了,Unagikuma 会察觉到,不会为每个监控项都给你发一遍告警。
- **状态页**,让你的用户随时了解服务状态。
- **随你一起成长。** 在网页上用一个加入码,一分钟就能加上第二台机器或整个集群。
- **从白到黑五种色调。** 纸白、雾灰、石板灰、石墨、墨黑,配上 Nagios 式的状态颜色,一眼看清。
- **轻松迁移。** 可以把 Uptime Kuma 或 Nagios 里的监控搬过来。
- **说你的语言。** 界面支持 15 种语言。

## 快速上手

**1.** 从 [Releases](https://github.com/githubflyideas/unagikuma/releases/latest) 下载适合你系统的文件并解压。

**2.** 运行:

```sh
./unagikuma
```

Windows 上运行 `unagikuma.exe`。

**3.** 在浏览器打开 http://localhost:8077,创建管理员账号。

**4.** 点击 **添加监控项**,填入网址,就完成了。

> 从另一台电脑打开?访问 `http://<服务器地址>:8077`,并输入程序首次启动时显示的 **初始化令牌**。

## 单机、双机、集群

> **鱼和熊掌,可以兼得。** 多数监控工具逼你二选一:要么小巧好上手,但只能守着一台机器;要么能扩展成集群,却得先装数据库、装代理,折腾一下午。Unagikuma 两样都要:一台机器、一个文件就能开干;想要更多,把别的机器加进来就行。同一个程序,同一个页面,不用迁移任何东西。

Unagikuma 首先是为一台机器设计的。检测、告警、状态页、历史记录,在一台机器上全都能用。多加机器,只是多了几个观察角度。

### 单机:立即可用

运行这个文件,加一个监控项,就完成了。不用装数据库,不用装代理,也不需要第二台服务器。大多数人就是这样用的,一台机器本身就够了。

![总览:从本机到每个目标,哪里断了一目了然](docs/images/overview.png)

### 双机:各自独立监控

在别的地方放第二台服务器,比如另一个办公室或另一家云服务商。在第一台上打开 **设置 › 节点 › 加入码**,在第二台上打开 **设置 › 节点 › 加入集群**,粘贴加入码。第二台会立刻拿到配置副本,马上开始检测。

- **两台各自检测、各自告警。** 任何一台宕机,另一台照常工作、照常发告警。
- **不瞎猜。** 两台互相联系不上时,谁也无法判断是哪一边断了网,所以谁都不会宣布对方挂了,两边都继续各自检测、各自告警。
- **每条消息都标明来源站点**(`[Tokyo] …`),你总能知道告警是从哪里发出的。

### 集群:多个站点,一张全景图

用同样的方法想加多少站点就加多少。每个站点依然各自检测、各自告警,所以任何一个站点掉线,包括主服务器,监控都不会中断。集群多出来的是全局视角:每个监控项、每条告警都会附上其他站点此刻看到的结果。

![一个故障监控项,以及每个站点看到的结果](docs/images/detail-sites.png)

- **是“全网都挂了”,还是“只是这里连不上”?** 各站点的观测结果让你一眼看出,是服务真的挂了,还是只有某条网络路径断了。过时的结果会明确标出。
- **站点失联只报一次:** 默认一分钟后发通知(可调),恢复后再发一条恢复通知。主服务器重启,不会引发一连串“站点不可达”的消息。
- **配置变更几秒内同步到所有站点,** 每个站点还可以保留只属于自己的监控项,比如那个办公室的路由器。

![节点页:每个站点的在线状态、往返时延和配置版本](docs/images/nodes.png)

## 告警洪水:一个问题,一条消息

为一根断掉的网线连发一百条告警的监控工具,最后只会被静音,然后就没用了。Unagikuma 把告警洪水当成必须防住的缺陷:

- **先看自己的网络。** 本机自己断网时,Unagikuma 会发现所有目标是一起失败的,只发一条关于网络的消息,而不是每个监控项各发一条。网络恢复后,被压下的监控项会分批重新检测,确认之后才报告。
- **先父后子。** 一台主机宕机时,它上面的服务不会一个个分别报警。
- **每个通道每分钟最多三条告警。** 超出的部分在这一分钟结束时汇成一条摘要,最严重的排在最前。新问题有单独的名额,不会被提醒消息挤掉;但一百个服务同时出故障,收到的仍然是一条摘要,而不是一百条消息。
- **好消息从不压着。** 恢复通知和升级告警总是立即发出,你不会苦等那条“可以停手了”的消息。
- **抖动会被汇总。** 一个时好时坏的服务,只算一个事件并附上次数,不会刷出一串故障和恢复。
- **计划内的维护保持安静。** 维护窗口内,你声明要动的东西不会告警。

所有阈值都可以在 **设置 › 可调参数** 里调整。

## 从 Uptime Kuma 迁移

先停止 Uptime Kuma，然后预览一下（不会做任何更改）：

```sh
./unagikuma import kuma --dry-run /path/to/uptime-kuma/data/kuma.db
```

确认无误后正式导入：

```sh
./unagikuma import kuma /path/to/uptime-kuma/data/kuma.db
```

报告会列出已导入的、需要查看的和无法导入的内容，并说明该怎么做。报告也会保存在 `data/import-reports/` 中。再次运行只会添加新的内容。

## 从 Nagios 迁移

指向 `nagios.cfg`，先预览一下（不会做任何更改）：

```sh
./unagikuma import nagios --dry-run /etc/nagios4/nagios.cfg
```

确认无误后正式导入：

```sh
./unagikuma import nagios /etc/nagios4/nagios.cfg
```

报告会列出已导入的、需要查看的和无法导入的内容，并说明该怎么做。报告也会保存在 `data/import-reports/` 中。再次运行只会添加新的内容。

## 忘记密码？

在运行 Unagikuma 的机器上执行：

```sh
./unagikuma reset-password admin
```

输入两次新密码（不会显示）。加上 `--generate` 可以改为自动生成一个随机密码。
